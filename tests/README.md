# tests/

**None of this is deployed.** Nothing here is served, linked, or read by `index.html`, and no part
of it ships to a user. It exists so a change to `index.html` can be *proved* rather than asserted —
`HANDOFF.md` §4 says "do not report a fix without evidence from a real browser", and this is the
apparatus that produces the evidence.

There is still **no test runner and no framework**. There is a harness, some fixtures and some
recorded baselines. You run a test by hand and read the numbers.

```
tests/
  fixtures/     real saved calendars, to test the restore path against
  harness/      the headless-Chrome harness: server, shared lib, tests, validators
  baselines/    recorded before-measurements, kept so nobody re-measures them
```

## fixtures/

`v1.0.0-saved.html` — a **genuine** pre-`.sptcal` calendar, produced by serving the v1.0.0 build
itself, typing a calendar into it and clicking Save. 760,003 bytes, 27 snapshot keys, no `version`
field, grid baked in.

This is the file that proves the compatibility rule in `CLAUDE.md`: *every saved calendar must keep
opening, forever*. Test the restore path against **this**, not against something today's code
wrote — the first `.html` compatibility test used a file generated by current code, which already
had the `version` field and no baked grid, and so proved only that the new code could read itself.

**Cut a new fixture every time a version is cut**, alongside the tag and the `releases/` copy. The
fixtures are worth having only if they keep pace with the formats out in the wild.

## harness/

See `harness/README.md`. One command per test:

```bash
cd tests/harness && ./run.sh base 45
```

## baselines/

A dated folder per investigation, holding the measurements and the actual exported files from
*before* a change. The point is that an acceptance gate needs a before-side, and re-deriving one is
an afternoon of work that has already been done once.

Each folder has its own README saying what was being measured and why.
